SQLite instead of PostgreSQL

PR D · plan · 2026-10-31 · after G and B, before C · branch off origin/master

Almanach is one process with one serial worker and its clones on a local volume: a database server buys it nothing. PR D moves the store to one SQLite file on its own volume, the database's own, apart from the clones; the deployment gets a PVC for it. PostgreSQL goes, not kept beside it. Nothing is built until this plan is approved.

1. Why, and why not both

  • One instance by design. One worker writes every page, one poller owns the clones, and the clones already need a volume on one node. A second replica is ruled out by the worker, not by the database.
  • Less to run. No database container in compose, no password, no DSN; in the cluster no external database order. A backup is the volume.
  • Faster, simpler gate. The store tests run against a temporary file: no docker, no SHIP_TEST_DSN, and a plain go test covers the store.
  • Small write load. Webhook deliveries, the worker's revisions and the poller's state: a few writes a minute. One writer at a time is plenty.

Not both. Two dialects, two schema sets, every store test twice and every later change written twice: a lasting cost for a choice made once.

2. Where the state lives

3. The store on SQLite

The driver is github.com/ncruces/go-sqlite3 (WASM, no cgo; 1,131 stars, last commit 2026-10-31) through database/sql, opened with kit's sqlitex.DSN (busy timeout 10 s, WAL, foreign keys) plus _txlock=immediate. Migrations stay on kit's migrate, switched from its PostgreSQL dialect (the advisory lock) to its SQLite one. pgx goes.

One schema, fresh. The five PostgreSQL migrations (and G's 0006) become one 0001_init.sql in SQLite's dialect: a new database, so nothing applied is edited.

The store's API stays as it is: callers (api, consolidate, clone, ingest) do not change, beyond the store opening from a path.

4. Writers and locks

Four places write: the webhook (a delivery, a note, the queue), the worker (revisions, run progress, the ledger), the poller (source and clone state) and the Quellen routes. Each write is a short transaction; none spans a model call or a git command.

  • Every writing transaction begins IMMEDIATE (_txlock=immediate): it takes the write lock at BEGIN, so it never holds a read snapshot and then fails its first write with "database is locked". A second writer waits up to the busy timeout (10 s).
  • Readers never wait in WAL: the UI and the API read while the worker writes.
  • The per-page advisory lock goes. It guarded a second worker that does not exist; with one writer at a time the page row's transaction is already serial.
  • A busy timeout that runs out is a persist failure: the webhook answers 500, as for any failed write today ("persist failure = 500, never swallowed" stays).

5. Configuration, startup, migrate

  • DATABASE_URL goes; ALMANACH_DB_PATH (required) names the file, e.g. /data/almanach.db. Its folder must exist and be writable, checked at startup as ALMANACH_REPOS_DIR is.
  • almanach migrate stays the one place that migrates, on the same path; serve never migrates and refuses a database whose schema is behind, as today.
  • /readyz asks the database (a SELECT 1), as today.
  • CONFIGURATION, HOW_IT_WORKS (storage model, operations), README and .env.example follow. AGENTS.md: the store line becomes "SQLite, one file on its own volume, WAL, writes BEGIN IMMEDIATE; never a shared filesystem", within the 4k.

6. Tests and the gate

  • testStore opens a migrated database in t.TempDir(): no skip, no docker. Every store test runs in a plain go test.
  • ship.yaml drops its PostgreSQL service and SHIP_TEST_DSN; CI no longer starts a database.
  • New tests: two writers at once (the second waits, both land), a busy timeout run out (a 500, nothing half-written), the fixed-width timestamps sorting as time, the JSON checks refusing invalid text.

7. Compose (PR C)

C is written after D, so it never has a database container. In rongo's shape:

  • almanach: ALMANACH_DB_PATH=/data/almanach.db, the data volume at /data and the repos volume at /repos, two volumes, never one.
  • migrate: the same image and data volume, almanach migrate, and almanach starts after it completes (depends_on: service_completed_successfully).
  • No POSTGRES_PASSWORD, no DSN in .env. The dev override keeps the same volumes.

8. The deployment repository

The deployment lives in its own repository, which has no remote: edited on its checked-out branch, no PR. Today it runs one replica with an external PostgreSQL, no volume at all, the sources off and proxy mode. In rongo's deployment's shape:

  • Two PVCs, ReadWriteOnce on the block storage class rongo's deployment claims: almanach-data (1 Gi, the database) and almanach-repos (20 Gi, the clones). Block, not a shared filesystem: SQLite in WAL needs POSIX locks on one node.
  • The deployment keeps replicas: 1 and Recreate (two pods on one RWO volume would not start, and must not). The data PVC at /data, the repos PVC at /repos; the migrate init container mounts the data PVC too.
  • Configuration: ALMANACH_DB_PATH=/data/almanach.db; DATABASE_URL leaves the sealed secret; the sources on (ALMANACH_REPOS_DIR=/repos, ALMANACH_SECRET_KEY sealed) (D5).
  • Its README (German) loses the database order and gains the PVCs.
  • Auth: B removes proxy mode, which this deployment runs with an OAuth sidecar. Its switch to oidc is the same kind of change (D6).

9. Decisions

D1 · decided (user)

SQLite only, PostgreSQL removed. The database on its own volume, apart from the clones; a PVC for it in the deployment, as rongo's.

D2 · decided: fresh start

Recommend a fresh start. The repository and project pages rebuild from the code by baseline runs; the sources are added again in Quellen. What is lost: the notes noergler delivered before the switch and the revision history.

Alternative: a one-off almanach import-postgres <dsn> that copies every table into the new file. About 250 lines and tests, and pgx stays a dependency until it is deleted a release later.

The deployment is a dev stage; if its notes matter, take the import.

D3 · decided: text

Recommend TEXT, UTC, fixed-width RFC 3339 with nanoseconds, written and parsed by the store: readable in the sqlite3 shell, sorts as text, keeps sub-second order (merges, run steps).

Alternative: INTEGER Unix nanoseconds: compact and exact, unreadable by hand. rongo's datetime('now') (seconds) loses the order of two merges in one second.

D4 · decided: G, B, D, C

Recommend G → B → D → C. G's migration 0006 lands in PostgreSQL and is folded into D's schema; B does not touch the store; C is written once, without a database container.

Alternative: D first, G on SQLite: G (being built now) would rebase onto a new store, a larger conflict than folding one migration.

D5 · decided: on

Recommend on, with the repos PVC: the code is Almanach's starting point now, and without the sources the deployment only folds notes.

Alternative: data PVC only, the sources stay off until later; one PVC and one secret fewer.

D6 · decided: oidc with the PVCs

Recommend: switch it to oidc in the same round as D's PVCs, after B and D are released: one change to the deployment, the OAuth sidecar removed. Needs the identity provider's client, which is yours to order.

Alternative: the deployment stays on the last release with proxy mode until the client exists.

10. Verification

  • make check without docker running: every store test runs, coverage floors hold.
  • A run of the binary on a fresh file: almanach migrate, serve, a webhook delivery, a source added, a baseline step written, /readyz green.
  • Compose (C): docker compose config shows two volumes and no published port; the stack comes up, the database file lands on the data volume only.
  • The deployment: kustomize build renders both PVCs, the mounts and no DATABASE_URL; the rollout itself is yours.
