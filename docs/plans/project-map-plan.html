1. Where phase 2 left things

Phase 2 (#10 to #17) is merged: a cloned repository is described from its code, a run per repository, the notes refine the page afterwards. Reviewing it left four follow-ups:

  1. What the model believes. Repository docs are read first, and nothing says the code wins when the two disagree. Diagram sources (.puml, .mmd) are never read by the overview. The project step sees one repository at a time, so the project description grows repository by repository instead of giving an architecture view.
  2. A login of Almanach's own, like ../rongo. Today Almanach has none (open) and proxy (trusts X-Forwarded-User, loopback only, used by the sidecar setup in the deployment repository). Neither fits a Traefik stack. rongo signs in over OIDC itself through ship/kit/auth. proxy is removed (user, 2026-10-31); the deployment repository switches to oidc.
  3. A compose.yaml like rongo's. Traefik in front, no host ports, hostnames and secrets in .env. Platform and sidecar specifics belong to the deployment repository, not to Almanach.
  4. An overview diagram on the project page: how the repositories and the systems around them are connected. The rest of the page says what a reader needs at the top level.

Phase 2's plan kept diagrams out of the wiki. PR G reverses that by the user's order; statements still render as paragraphs, never markdown, and a diagram is structure beside them, not text inside them.

2. What a project page holds

A reader opens the project page to answer three questions: what is this system, which repository do I touch, and what will I break. Each element maps onto a shape Almanach already has, except the map:

#ElementShapeWhat it says
1Purpose and boundarysummaryWhat the system does, for whom, and what is explicitly outside it.
2System mapmap, new in PR GThe repositories and the external systems they depend on, each connection typed by kind.
3Repository rolessummary, by slugKind (service, UI, library, tooling, infra), what each owns, exposes and consumes. One paragraph each; the detail stays on the repository page.
4Interfaces between repositoriescomponentAPIs, event schemas and shared libraries, and which repository owns each. This is where breaking changes live.
5Shared entitiesentityEntities that cross repositories, which repository is the system of record, how identifiers travel.
6Cross-repository rulesrule / invariantOrdering, idempotency, consistency, auth or tenancy boundaries that span services.
7Key flows end to endsummary or a statementThe one to three paths that cross the most repositories, told against the map's nodes.
8Runtime topologysummary, briefWhat is a deployable unit, what talks to what at runtime as opposed to build time. Only what code shows (manifests, compose files, Containerfiles); no environments.

Left out: each repository's tech stack (the file names say it), anything a repository page already holds, changelogs.

6. PR G: diagrams like rongo's, an overview map on every project

The user's order: ../rongo-style diagrams wherever a diagram fits, and an overview diagram on every project. The look and the drawing are rongo's: its layout, its drawing, its --diagram-* theme.

The model returns structure, code validates it, the UI draws it with rongo's code. The model sends no Mermaid and no markdown: the structured JSON is rongo's intermediate form (ui/src/diagramIR.ts: FlowIR, SeqIR, the ER form). That keeps "paragraphs, never markdown", keeps validation in Go, and saves the Mermaid dependency.

Two places get diagrams

  1. The project overview map, mandatory. The project step's answer must carry map, a FlowIR of nodes, edges and zones. Without it the call is off schema: the project step is skipped and redone next time. Zones by kind: clients, repositories, stores, external systems. Repository node ids are slugs, and a repository node links to its page. Edge labels name how the parts talk: HTTP, event, DB, library, file.
  2. Statement diagrams, optional, where a picture says more than the paragraph. A statement may carry diagram of one kind: flow (a flow or a state machine), sequence (an exchange between parts), er (entities and their relations). The baseline steps (describe, project) and the PR merge path may all set one. An edit returns the full statement, diagram included; the prompt shows the existing diagram, so keeping it means repeating it, exactly as with the text.

Schema and validation

  • Strict JSON with anyOf over the three kinds, in inference/baseline.go. The merge schema in inference/inference.go gets the statement diagram too.
  • A new baseline/diagram.go, in the same register as the provenance rules. An invalid diagram rejects the rewrite whole and the page stays.
  • The map: a repository node must be a source repository slug of the project. An unknown slug is an invention.
  • Every diagram: every edge end and every message end is a declared node or participant; no self edges, no duplicates; labels go through lang.SwissSS and are capped in length.
  • Every node, external, store and client nodes as much as repository nodes: a unique id, a kind from the fixed list, a label that is not empty.
  • Caps from config: ALMANACH_DIAGRAM_MAX_NODES (12) and ALMANACH_DIAGRAM_MAX_EDGES (20) per diagram, ALMANACH_MAX_DIAGRAMS (6) statement diagrams per page, repository or project page; the project map does not count toward it. Past about 12 nodes it is two diagrams; the prompt says so (D8).
  • AGENTS.md, within the 4k: "statements as paragraphs, never markdown" gains "diagrams only from validated JSON, drawn by rongo's code". Section 14 of the baseline plan ("no diagrams in the wiki") is superseded by the user's order.

Storage

  • Statement diagrams live in Statement.Diagram, inside the statements JSONB that already exists (0001_initial.sql:140): no column.
  • The project map: a new migration 0006_diagrams.sql (0005 is the retry trigger) adds revisions.map JSONB NULL, project scope. No applied migration is ever edited.

8. PR B: OIDC login like rongo

Modeled on rongo's backend/internal/auth/{session.go,middleware.go,claims.go}, internal/httpapi/auth_handlers.go, cmd/rongo/main.go (oidcConfig, discovery with a 30 s timeout) and the ui/src/App.tsx session gate. Slimmer than rongo: no users table, no password or token modes. Almanach's read API gates nothing on the user; the name goes to the access log.

Config

  • ALMANACH_AUTH_MODE takes none | oidc. proxy is removed (D1): the enum drops it, so proxy fails startup with config's enum error; the loopback check (config.go:141), the X-Forwarded-User read (api.go:198) and every test of them go.
  • With oidc, mandatory and each refused under the other mode (rongo's rule): ALMANACH_OIDC_ISSUER (bare origin), ALMANACH_OIDC_CLIENT_ID, ALMANACH_OIDC_CLIENT_SECRET, ALMANACH_OIDC_REDIRECT_URL (https; the cookie's Secure flag comes from it), ALMANACH_SESSION_SECRET (at least 32 bytes).
  • oidc allows any SERVER_HOST.

Backend

  • New backend/internal/auth: NewSessions (kit's signed cookie almanach_session, 30-day TTL), Claims = kitauth.Claims, a middleware.
  • In oidc mode every /api/* route needs a session and answers 401 JSON without one, except /api/auth/login and /api/auth/callback. /webhooks/noergler, /auth/ping, /healthz and /readyz are untouched: bearer or open, as today. The SPA shell (static, no data) is served without a session, as in rongo.
  • Routes: GET /api/auth/login (OIDC.Start); GET /api/auth/callback (sets the cookie, redirects to /; on failure to /?auth_error=…); POST /api/auth/logout (clears the cookie, returns {redirect_url}); GET /api/me ({mode, user} in every mode, 401 only in oidc without a session).
  • Deps.user reads the claims (email, else subject) in oidc mode; in none mode it stays anonymous.
  • main.go: OIDC discovery at startup with a 30 s timeout. A failure is a fault and the process exits, as in rongo. kitauth.OIDCConfig gets scopes openid profile email and the cookie prefix almanach_.
  • go get github.com/trick77/ship/kit/auth@latest: a ship-family module, never pinned by hand.
Changed by review · 2026-10-31

The review of the PR changed four points above; the code follows these, not the lists.

  • Discovery is a warning, not a fault. It runs in the background from startup on (30 s an attempt, retried after 5 s, doubling up to 5 min, each failure logged); boot never waits for it. Until the provider answers, the webhook, the ping and the probes work, the wiki stays behind its 401, and the login and callback land on /?auth_error=provider_unavailable, where the UI halts with a button to try again.
  • The issuer is taken as written, not as a bare origin: discovery compares it byte for byte, so a path and a trailing slash stay. https, plain http only on a loopback host for a local provider; no user info, query or fragment.
  • The redirect URL is parsed: https, a host, and the path exactly /api/auth/callback. The cookies are always Secure.
  • CSRF: in oidc mode a POST, PUT, PATCH or DELETE under /api passes Go's CrossOriginProtection (Sec-Fetch-Site, else Origin against the host; the redirect URL's origin trusted), and a write carrying neither header is refused; else 403. SameSite Lax alone lets a sibling subdomain post.

Also from the review: a deep link survives the sign-in (?next=, a same-site path only, kept in the almanach_next cookie for 10 minutes); the reader's name is kit's Username() (preferred username, else email, else subject); any 401 in oidc mode signs in again, guarded against loops.

UI

  • A session gate in App.tsx like rongo's, states checking, in, out and halted. On 401 a full navigation to /api/auth/login. ?signed_out and ?auth_error halt with a button instead of redirecting.
  • The header's right slot, already reserved for this (App.tsx comment), shows the reader's name and "Abmelden", in oidc mode only.
  • German copy in strings.ts; tests in pages.test.tsx.

Docs

  • CONFIGURATION gets the oidc variables. The section "The sidecar" and every mention of proxy mode, the sidecar and X-Forwarded-User go: CONFIGURATION, README, HOW_IT_WORKS, AGENTS.md (the loopback rule), .env.example, openapi.yaml, code comments. Platform specifics live only in the deployment repository, which this PR does not touch.
  • README's production paragraph describes oidc behind Traefik. .env.example and openapi.yaml gain the auth routes and /api/me. AGENTS.md: the auth line, terse, within PR T's 4k.

Tests

  • Config validation per mode. Middleware: 401 without a cookie, through with a valid kit cookie, the webhook and ping pass without one.
  • The callback against an httptest fake issuer if kit/auth's tests offer one (rongo's auth_handlers_test.go is the model); otherwise the handlers behind an interface, with a stub.

9. PR C: compose behind Traefik

compose.yaml: the production stack, rongo's shape

  • almanach: build plus image: ghcr.io/trick77/almanach:latest (the name the ship release publishes, checked before the PR). No ports; on the external traefik network and the default network. Labels: Host(`${PUBLIC_FQDN:?…}`), entrypoint websecure, tls: "true", service port 8080, traefik.docker.network: traefik.
  • ALMANACH_AUTH_MODE: oidc is hard-coded, not interpolated, so a stray none in .env cannot open the stack.
  • Hardening: user: "1000:1000", read_only: true, tmpfs: /tmp, HOME/TMPDIR=/tmp for git, cap_drop: [ALL], no-new-privileges. init: true: rongo had 192 zombies in 13 h from git's detached helpers.
  • stop_grace_period: 11m. The worker waits CallTimeout + 15s (10 m 15 s, main.go:286) for a paid call in flight; Docker's default of 10 s would kill it.
  • env_file: {path: .env, required: false}. Team keys: the directory ./conf:/conf:ro with ALMANACH_TEAM_KEYS_PATH=/conf/team-keys.json; mounting the directory avoids Docker turning a missing file into a directory. The healthcheck stays the image's exec probe.
  • postgres: no ports, default network only. POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?…}; the DSN is composed from it, hex only (openssl rand -hex 24), because the password sits in a URL.
  • migrate: unchanged apart from the DSN. Named volumes pgdata and repos stay; the image's /app/repos gives the empty volume uid 1000, so no chown step.
  • A header comment with the first-run steps, like rongo's.

compose.dev.yaml: the override for local work

  • docker compose -f compose.yaml -f compose.dev.yaml up: host ports 5433 and 8081, ALMANACH_AUTH_MODE: none, POSTGRES_PASSWORD default changeme.
  • The traefik network redefined as not external, verified with docker compose config. If the override cannot turn external off, the dev file creates its own network and the README names it.

Docs

  • .env.example: PUBLIC_FQDN and POSTGRES_PASSWORD as active lines; the oidc block comes from B.
  • README quickstart switches to the dev override; CONFIGURATION is updated.
  • team-keys.example.json moves to the conf/ hint, and conf/ goes into .gitignore.

10. Decisions

Three are decided by the user and marked so. The others are recommendations with their options and cost; the code follows the recommendation unless it is overruled.

D1 · Proxy mode removed · decided

Decided (user, 2026-10-31): removed. ALMANACH_AUTH_MODE is none | oidc; proxy fails startup with config's enum error, the loopback rule and the X-Forwarded-User read go.

Cost: the sidecar setup in the deployment repository breaks on the release that carries PR B until it switches to oidc; that is accepted. The option of keeping proxy beside oidc was set aside: two auth paths to keep in step, one of them trusting a header.

D2 · Diagrams in rongo's style · decided

Decided (the user's order): ../rongo-style diagrams wherever a diagram fits. The model returns rongo's IR as strict JSON, Go validates it, the UI draws it with rongo's copied layout, drawing and theme. No Mermaid: not from the model, not in the store, not in the UI.

Cost: about 2,400 copied lines plus tests in the UI (D9), one dependency (elkjs), a new validation file and a migration.

D3 · Every project gets an overview map · decided

Decided (the user's order): the map is mandatory on every project. The project step's answer without map is off schema; the step is skipped and redone at the next run.

Cost: every project call returns a map, a few hundred output tokens; a project with a single repository still gets one, its externals around it.

D4 · Who may change sources in oidc

Recommend every signed-in user, as every caller may today. Who gets in at all is the identity provider's policy.

Options: this (recommended); or ALMANACH_OIDC_ADMIN_GROUP gating the source writes on a groups claim.

Cost: anyone the identity provider admits can add, change or remove a source and its token. The group gate is a few lines, but a second gate to keep in step with the identity provider's groups.

D5 · none on a non-loopback host

Recommend it stays allowed: compose.dev needs 0.0.0.0 inside the container. compose.yaml hard-codes oidc instead, so production cannot fall back to open by an .env line.

Options: allowed (recommended); or refused like rongo's dev mode, which makes the dev override bind loopback and forward the port by a trick.

Cost: a hand-run binary with none on a public interface is open; the guard is the compose file, not the code.

D6 · Sibling summaries in the PR merge path

Recommend no, wording only. The merge prompt's project paragraph gets the architecture wording of section 2; the other repositories' summaries stay a baseline project step input.

Options: no (recommended); or yes, the same {other_repos} block on every merge.

Cost: between baseline runs a PR's project fold sees only its own repository. The alternative costs about 1 to 2 kB more input per repository on every merged PR.

D7 · Who updates the system map

Recommend only the baseline project step, on full runs and the monthly reconcile. The merge path carries the map forward unchanged.

Options: baseline only (recommended); or the merge path rewrites the map too, which needs the map schema plus every repository's summary on every PR, roughly doubling the merge call's input.

Cost: a PR that adds a dependency shows up in the map at the next reconcile, or on "Aktualisieren".

D8 · Diagram caps

Recommend 12 nodes and 20 edges per diagram, 6 diagrams per repository page, from config. Over a cap the rewrite is rejected whole, like every other ceiling; never truncated.

Options: these (recommended); or higher caps.

Cost: a large system has to be drawn as two diagrams, and the prompt says so; a model that ignores it loses that rewrite's call. Past about 12 nodes a diagram stops being readable anyway.

D9 · Copy rongo's drawing code

Recommend a copy, each file headed as a copy of rongo's, kept in step by hand.

Options: copy (recommended); or a shared package both repositories import, which ends the drift but is its own project, later.

Cost: about 2,400 lines that drift unless both sides are touched together. elkjs 0.9.3 comes with it: 2,867 stars, last commit 2026-10-28.

D10 · Library edges from manifests

Recommend later (v2): code reads go.mod/package.json for sibling modules.

Options: later (recommended); or now, deterministic, but mapping a module path to a slug is guesswork.

Cost: until then a library edge is only as good as the model reads it from the summaries.

D11 · .drawio in the overview

Recommend out: XML layout noise.

Options: out (recommended); or in, at the cost of bytes for coordinates in the overview's 160 kB.

Cost: a repository whose architecture lives only in a draw.io file has it unread; the code steps still read the code.
