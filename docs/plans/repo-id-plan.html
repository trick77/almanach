Projects and repositories are ids, their keys names

Plan · 2026-11-01 · branch worktree-repo-id off origin/master (8068015)

Renaming a project key or a repository slug today means rewriting ten tables, the text of every page and the clone folders, because key and slug are what everything joins on. This plan gives every project and every repository a fixed number and keeps its key or slug in one place. Afterwards a rename is one row, a change of case included (ACME → acme). A Bitbucket repository rename is picked up by the listing on its own; a project key and a hand-entered repository get a rename field under Quellen. Nothing changes for noergler. One PR. Nothing is built until this plan is approved.

1. Why a rename touches everything

A project is known as its project_key, a repository as (project_key, slug), everywhere. Nothing holds either once and points to it; every table carries its own copy, and two copies sit inside text:

WhereHow key and slug sit there
projects, sourcesthe project key is the primary key
repos, source_repos, baseline_runskey and slug are the primary key, or a foreign key to it
notes, note_calls, claims, revisions, pages, llm_callsproject_key, repo_slug: key or join columns
PR keys (PROJ/slug#42)notes.pr_key, source_pr_key, every statement's sources in the revision JSON; the UI builds note links from them (routing.ts notePathFor)
Clone foldersBACKEND_REPOS_DIR/<project>/<slug>
Two registriesnoergler's repos and the clones' source_repos, both keyed by key and slug; read.go reposFrom(sourced) switches between them

Two consequences. A change of case is a different key: a source entered as ACME while noergler delivers acme ignores every note, which is why creating a source refuses that spelling today (ProjectSpelledOtherwise), and an existing one cannot be fixed. And Almanach cannot see that a repository was renamed: the Bitbucket listing reads only the slug, so a rename looks like "NEW added, OLD missing", and with auto_describe on NEW gets a paid full baseline run beside OLD's page.

2. The fix: one table owns each name

  • projects becomes the project's identity: id INTEGER PRIMARY KEY, the current key, noergler's team and times (empty for a project noergler never delivered for). sources hangs off it by project_id.
  • repos becomes the repository's identity: id, project_id, the current slug, and forge_id: Bitbucket's numeric repository id, which survives a rename. Both noergler's ingest and the clone listing register into this one table.
  • project_names, repo_names map every key and slug ever used to its id, the current one included. A note, a link or a listing entry under an old name lands on the same project or repository. A name once used stays with its owner for good: it is never given to another project or repository (D5, user).
  • Every other table carries repo_id (repository scope) or project_id (project scope) instead of project_key and repo_slug.
  • Names are resolved at the edges only: the webhook and the API routes turn a key or slug into an id via the name tables; everything behind them works on ids. Responses still carry key and slug, read from projects and repos.

5. One PR

store: projects and repositories are ids, their keys names, on master (user, 2026-11-01: single PR). What a user sees afterwards:

  • Rename fields under Quellen: the project key on the source page, the slug on a hand-entered repository, a change of case included. Old URLs land on the new name.
  • A repository renamed in Bitbucket keeps its page after the next sync; no duplicate, no new baseline run. Precondition: the repository was listed once after the release (that listing records its forge_id by slug). Rename in Bitbucket before that first listing and it still looks like "NEW added, OLD missing": deploy, sync once, then rename.
  • Clone folders renamed to numbers on disk (D1); nothing re-cloned.

Commits inside the PR keep it reviewable in order: (1) migration 0002 and the store on ids, every existing test passing unchanged; (2) clone folders by id with the marked carry-over; (3) rename in store, API, openapi.yaml, UI; (4) listing by forge_id with the marked backfill; (5) AGENTS.md.

6. Migration 0002

0002_ids.sql; 0001 is never edited; serve never migrates. SQLite cannot change a primary key in place, so each table is rebuilt: create new, copy, drop old, rename.

  1. Build projects anew with id: one row for every distinct project key found in any table, sources and ledgers included. noergler's team and times are copied where they exist and become nullable: a project only a source knows has no team.
  2. Build repos anew with id and project_id: one row for every distinct (project_key, slug) in repos, source_repos, notes, note_calls, claims, revisions, pages, llm_calls, baseline_runs. A slug only the ledgers know (a removed clone) still gets its id: the ledger outlives a removed repository. Team and times nullable, as for projects; forge_id starts empty (filled by the first listing after the release).
  3. project_names, repo_names: one row each, the current name.
  4. Rebuild the other tables with project_id or repo_id from a join on the old key columns, which are then dropped. sources keyed by project_id, source_repos by repo_id, baseline_runs references it with the same cascade. Project scope: repo_id NULL with project_id set; pages keeps one primary key over (scope, project_id, COALESCE(repo_id, 0)). notes, claims keep their foreign key to teams.
  5. Indexes recreated on the new columns (queue, per-repository, per-project, the one-open-run index).
  6. Checks at the end: row counts per table equal before and after; PRAGMA foreign_key_check empty. A mismatch aborts the migration; the database stays on 0001.

The migration touches no JSON and no text: statements, summaries, maps and PR keys are copied byte for byte.

Transitional code, marked for removal

Every piece of code that exists only to carry existing installations over is marked with one grep-able comment, its removal condition included, so it can be deleted later: // TRANSITIONAL(ids): <what it does>. Remove when <condition>. git grep 'TRANSITIONAL(ids)' lists all of it; the PR description lists them. Tests that exist only for that code carry the same marker and go with it.

CodeRemove when
Poller moves an old <project>/<slug> clone folder to p<project id>/r<repo id>Every running instance has completed one sync cycle on a release with this change (no slug-named folder left)
ApplyListing fills an empty forge_id by matching the slugEvery listed repository has a forge_id (SELECT COUNT(*) … WHERE origin = 'listed' AND forge_id IS NULL is 0 on every instance)

Not transitional, so not marked: migration 0002 (migrations stay forever), the old-name redirects and name tables (the point of the change), ProjectSpelledOtherwise (still guards new sources).

7. Decisions

D1 · Clone folders · decided

By id, p<project id>/r<repo id> (user, 2026-11-01: folder names don't matter). A rename never touches the disk, a change of case included, which a case-insensitive filesystem would otherwise trip over. Existing folders are moved once by the poller on its first cycle, under its disk lock, so nothing is re-cloned.

D5 · A name once used · decided

Never reused, except a change of case on its own name (user, 2026-11-01). A key or slug stays with the project or repository that had it, in the name table, for good. "Used" ignores case: if another project ever had ACME, both ACME and acme are refused (409); the project that had ACME may become acme. The check folds case in Go, as ProjectSpelledOtherwise does today. The Bitbucket listing showing a new repository under a former name of another one does not add it: the source page shows the conflict and the log names it. Old URLs and old PR links can never point to the wrong project or repository.

D2 · PR keys after a rename · decided: A

A (recommended, taken 2026-11-01): keep them as merged. A PR merged as PROJ/OLD#42 keeps that label; it is history, noergler's own value, and it sits inside the statements JSON. Note links resolve through the name tables, so every chip still opens the right note. Cost: old PRs show the old name on the chip.

B: rewrite them on rename. Every chip shows the new name. Cost: the rename becomes a text rewrite across notes, revisions (inside the JSON) and llm_calls again, the exact thing this plan removes.

D3 · Notes between a Bitbucket rename and the next sync · decided: A

A PR merged under NEW before the listing has seen the rename arrives with a slug Almanach does not know in a sourced project: 202 ignored, never stored, as AGENTS.md requires. The window is up to BACKEND_SYNC_INTERVAL (30 min by default). The same holds for a project key changed in noergler before it is renamed in Almanach.

A (recommended): accept; rename in Almanach (or press "Synchronisieren") right after the change upstream. Cost: a merge in those minutes is missing from the wiki.

B: an unknown slug in a listed source triggers a listing right away. Cost: a Bitbucket call driven by the webhook, and the note that triggered it is still ignored, so it only shortens the window.

D4 · Sources off · decided: A

A (recommended): no rename without sources. With BACKEND_REPOS_DIR unset there is no Quellen page and the wiki is read-only; a renamed project or repository then starts a new page, as today. Cost: none for the production setup, which runs with sources.

B: rename fields outside Quellen. Cost: a second write surface in a wiki that is read-only by rule.

D6 · Names that differ only by case · decided: A

Today ACME and acme are two different projects. A source in one spelling while noergler delivers the other ignores every note.

A (recommended): exact match, plus the rename. Names are matched byte for byte, as today; a case mismatch is fixed by renaming once (figure 2), and ProjectSpelledOtherwise keeps refusing a new source in the other spelling. Cost: none beyond today; one rename per mismatch.

Built (review, 2026-11-01): lookups match exactly; a registration (an accepted note, a revision) under a spelling another project or repository had in another case joins it as a further name instead of making a second one, so D5 holds without a rename. Claims are kept by name as noergler sent them and register nothing.

B: match names case-insensitively. A note under acme lands in the source ACME without any rename. Cost: case folding in Go on every lookup (SQLite's lower() folds ASCII only), a folded unique column per name table, and two spellings of one project in links and PR keys for good.

9. Verification

  • Ids: every existing test passes without edits to its assertions. A migration test fills 0001 with each table's rows (project scope, a removed clone in the ledgers, an open run, a source noergler never delivered for), migrates, and compares every page, note and cost the API serves before and after. make check.
  • Rename: store and API tests: rename a project key by case only (ACME → acme), then a note delivered as acme lands on the existing project page; rename a hand-entered repository; 409 for a name ever used by another, in either case (ACME once used by project 1 refuses acme for project 2), and for an open run. Playwright against the running app: both rename fields under Quellen, the pages under the new names, the old URLs landing on the new ones, an old PR chip reaching its note.
  • Listing: listing test: same forge_id, new slug → one repository, slug changed, no new row, no run queued; a listed repository under another's former name → not added, conflict shown.
  • Upgrade on a copy of the production database before release: migrate, start, compare the project list and a few pages with the old version; clone folders moved, nothing re-cloned.

10. The renames you need now

A project key that differs from noergler's only by case: the rename field on the source page. A repository slug: the field for a hand-entered repository; for a listed one, sync once after the release (rename in Bitbucket, then press "Synchronisieren").
