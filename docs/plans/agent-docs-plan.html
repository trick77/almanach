Pages for agents first, onboarding second

Plan · 2026-10-31 · after the step-budget PR · branch off origin/master

The main reader of a repository page is a coding agent about to change the repository; the second is a developer in their first weeks. Both need the same facts in a different order. This plan gives the page three more kinds of statement, a fixed summary order, pitfalls from what actually broke, and a Markdown export an agent pulls into its context. Nothing is built until this plan is approved.

1. Two readers, one page

An agent opens a page to change code without breaking it: what must not break, where to make a change, why things are as they are, what broke before, how to check its work, each with the files it touches. A newcomer opens the same page to understand the system: purpose, structure, flows, words. Today the page serves the second reader well and the first by accident: rules and invariants are there, but where to change what, the decisions and the pitfalls are buried in prose or missing.

The classic architecture-documentation templates were written for people explaining a system to people. Their building blocks, runtime flows, cross-cutting concepts, decisions and glossary carry over and serve as a checklist here. Goals, stakeholders and quality scenarios an agent hardly needs; and they lack what an agent needs most: where to change what, how to verify, checkable rules, what broke before.

3. Three new kinds

  • decision: a choice the code embodies, its reason and what was given up ("one serial worker, not a pool: two writers of one page would lose a rewrite"). It keeps an agent from "fixing" what is deliberate. Mostly from PR notes, which carry the why; from docs and code comments where they state a reason; never guessed from code alone. Names the files that embody it.
  • extension: where and how a kind of change is made: to add a route, a step, a source kind, a setting, touch these files, in this order, register here. A change recipe for an agent, as terse as the change. Every file it names must be in the tree, as for any statement.
  • pitfall: something that broke in this code and how not to break it again. From evidence only (section 5). Names the files.

Statement rules stay: files required (at most 5), provenance by id, a PR statement dropped only when all its files left the tree, the page ceilings and the step budget. The project page may hold decision and pitfall across repositories; extension is a repository's.

4. The summary's order

The repository summary keeps its prose in a fixed order: purpose and boundary; structure; key flows; working on it last and short (the gate and test commands, conventions, what the repository's agent notes insist on). An agent jumps to the end, a newcomer reads from the top. The project summary keeps the order it has.

5. Pitfalls only from evidence

A pitfall needs proof that something broke; a code step may not infer one from reading code or from a TODO comment. Two feeds of proof, both already in Almanach:

  • Bugfix notes, merge path: noergler marks a note as a bugfix with its cause; the merge prompt routes it to a pitfall (new, or deepening one on the same files).
  • Problem areas, baseline: the directories bugfixes keep touching (bugfix_area), with count, top cause and the newest fixes' PR keys. A subject step gets the problem areas its files sit in, as data beside the files, and may write a pitfall where the code shows how the fixes' cause arises. Without a problem area for its files, a subject step writes none.

A pitfall carries the PRs that evidence it as its sources, as any statement does, so a reader sees what it rests on.

6. The Markdown export

  • GET /api/projects/{key}.md and GET /api/projects/{key}/repos/{slug}.md, text/markdown, from the current revision: the summary, then the statements grouped by kind in the order invariants, rules, decisions, pitfalls, extensions, components, entities; each with its files and PR keys; a statement diagram as a fenced JSON block.
  • Statements stay paragraphs: Markdown is only the export's frame (headings, file lists), never inside a statement.
  • An agent outside a browser has no session in oidc mode: D3.

7. What changes where

  • Kinds: decision, extension, pitfall in the strict schemas, the code's kind list, the three prompts' output formats, openapi.yaml and api.ts, the UI's labels and order. No migration: kinds live in the statements JSON.
  • Prompts: the describe and merge prompts define the kinds and the summary order; a pitfall only with evidence; a decision only with a stated reason; the merge prompt routes bugfix notes to pitfalls.
  • Problem areas into the subject step: the store's problem query, filtered to the step's directories, rendered as untrusted data.
  • Export: two read routes, a renderer of its own, the contract.
  • Docs: HOW_IT_WORKS (page model), CONFIGURATION if D3 adds a setting, AGENTS.md one terse line if an invariant arises.

8. Decisions

D0 · decided (user)

No technical debt on the page; pitfalls only from evidence that something broke. The classic templates are a checklist, not the structure.

D1 · decided: all three

Recommend all three: decision, extension, pitfall. Each answers a question an agent asks before it edits.

Alternative: decision only. Cheaper; where to change and what broke stay unanswered.

D2 · decided: problem areas plus bugfix notes

Recommend: problem areas beside a subject step's files, plus the merge path's bugfix notes.

Alternative: the merge path only. No new prompt input; a repository whose bugfixes predate noergler never gets a pitfall.

D3 · decided: team bearer opens the .md routes

Recommend: the team bearer tokens also open the two .md routes, read-only. No new secret, no new table.

Alternatives: separate read tokens (one more key file and rotation); session only (an agent outside a browser cannot read).

D4 · decided: one file per repository and project

Recommend one file per repository and one per project. A project bundle can follow; large projects would overflow a context.

D5 · decided: later

Recommend later, its own plan. Querying by topic or file is where embeddings start to pay.

9. Verification

  • make check: the schemas offer the kinds; the export renders a fixture page in the documented order; the bearer opens only the .md routes; an extension or pitfall with invented files is refused.
  • The prompt eval on almanach and rongo: extension statements name real files and registration points; pitfalls appear only where a problem area or bugfix note backs them; the summary ends with how to work on the repository.
  • An agent test: hand one repository's export to a coding agent with a small change request and check it touches the files the extension statement names.
