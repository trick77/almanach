Project and repository pages: tabs, rail, repository map

The project page is one long column: the map, then a description that runs for screens, and the repositories, problem areas and notes only after it. The repository page has the same shape. This plan splits both pages into two tabs with a sticky rail beside them, adds a search over the description, and gives every repository page a map of its own, drawn by the baseline run.

1. Decided

Settled in the mock rounds, recorded here so the build does not reopen them.

Decided · layout

Two tabs plus a rail on both tabs (mock variant D). The rail lists the sections of both tabs; a link into the other tab switches it, then jumps. Because the rail never leaves, the content column never moves sideways on a tab switch. Rail and content start on one top edge: the search input, the breadcrumb and the first column line all sit at the same y (measured in the mock, 112px at 1440×900).

Decided · project page

Tabs Übersicht (start: Systemkarte, Repositories, Problemzonen, Letzte Notizen, full tables as today) and Beschreibung (summary, statements by kind). The project page is the hub; what sits at the very bottom today comes first.

Decided · repository page

Tabs Beschreibung (start: Aufbau map, summary, this repository's problem areas, statements by kind incl. Erweiterungen) and Verlauf (Notizen, Revisionen). The repository page is a leaf: content first; notes and revisions are provenance. The rail adds a group Projekt <KEY> listing the project's repositories, the current one marked, always open; with many repositories the rail scrolls inside itself (it is capped at the viewport's height).

Decided · search

An input at the top of the rail filters this page's description only: statement name, text and files, client-side, no backend. Matches are highlighted, the rail's counts become hit counts, empty kinds dim, a line under the input reads „2 von 23 Einträgen“. / focuses, Escape clears. Typing on the other tab switches to Beschreibung.

Decided · tab in the URL

The hash holds the tab and nothing else: #beschreibung, #verlauf, none for a page's start tab. A shared link opens the right tab; a reload keeps it; returning to the page with back/forward restores the tab it was left on. A tab switch replaces the hash (history.replaceState), so back/forward does not step between tabs, it leaves the page. Rail section links never touch the hash: they scroll (preventDefault, scrollIntoView), else a click would overwrite the tab. No new route: routing.ts and backend/web/embed.go stay as they are.

Decided · repository problem areas

From the project endpoint the repository page fetches anyway for its rail, filtered by repo_slug. No backend change; the window is the project's (problem_window_days).

Decided · Entitäten on the project page

The kind stays (the project prompt defines it as entities that cross repositories, their system of record and how ids travel); its label on the project page and in the project's .md export becomes „Geteilte Daten“. The repository page keeps „Entitäten“. No prompt or data change.

Decided · diagram links, breadcrumb

Repository nodes on the Systemkarte link to the repository page (as today) also in the full view (DiagramView), with a hover that reads as a link. The breadcrumb sticks while the page scrolls, on the rail's top edge.

Decided · repository map

Every repository page leads with Aufbau, a flow map of the repository from inside (entry, parts, what they talk to), drawn by the model in the baseline run, checked like the Systemkarte. A merge does not redraw it; it carries it forward, as it carries the Systemkarte today.

4. Repository map

One PR, baseline: a map on every repository page. The Systemkarte's machinery, pointed at one repository: a flow diagram, checked by baseline.CheckMap's rules, stored on the revision, carried forward by merges.

Pieces

  1. Migration 0004_repo_map.sql (decision 5.1): ALTER TABLE revisions ADD COLUMN repo_map TEXT CHECK (json_valid(repo_map)) CHECK (repo_map IS NULL OR scope = 'repository'). Additive on revisions; 0001 to 0003 untouched. serve never migrates; almanach migrate applies it.
  2. Store: Page.RepoMap, NewRevision.RepoMap, read in CurrentPage, written in insertRevision. Three writers make repository revisions: a merge (consolidate.go:432), every describe step of a run (foldPatch, baseline.go:708 via ApplyBaselineStep) and the new map step. Only the map step brings a map; the other two must not erase it, or the first describe step of the next run, or the first merge, would leave the page without one until a map step runs again. So insertRevision carries it in one place: a repository revision without RepoMap takes the current page's. Nothing ever removes a repository map (the step's null means keep), so the store-level carry needs no "clear" case.
  3. Prompt almanach_repo_map.txt (compiled in): the repository from inside, flow LR, zones by fixed ids entry, parts, stores, external; edge labels start HTTP, event, DB, library, file, call; at most DrawMaxNodes/DrawMaxEdges; it is no statement diagram and does not count toward their number; only what the description shows; the current map shown, returned unchanged when nothing changed. Answer {"map": <flow> | null}.
  4. Check: baseline.CheckRepoMap: checkFlow plus the zone set above; no slug rule (nodes are parts, not repositories). Over a cap or broken: not stored, the previous map carried, logged, as revisionMap does.
  5. Step: repoMapStep in consolidate/baseline.go after projectStep, before finish. Order by budget: placed before, it could take a run's last call and leave the project step "calls are spent" where it runs today; after it, the Systemkarte keeps today's priority and the repository map is the first thing dropped under a tight budget. Every path out of projectStep that calls finish today (skip, no repository description, calls spent, done) hands over to the map step instead. One Chat, strict schema, no in-call retry, the project step's model profile (no new config).
  6. As built, after review: the map step writes no revision. It sets repo_map and repo_map_basis (sha256 of the text it was drawn from) on the page's current revision in place (SetRepoMap, with the run's save); every later repository revision carries both. It calls only when no map exists or the basis no longer matches the text, so a skipped or refused map, or one a merge made stale, is redrawn by the next run, quiet reconciles included. A busy write that exhausts its attempts ends the run done, without the map. maxSubjects keeps one call for it (MaxCalls-4).
  7. API: repoDetailBody.Map (map, flow or null); openapi.yaml in step. The .md export writes it after the summary, as the project export writes the Systemkarte.
  8. UI: section Aufbau first on the repository's Beschreibung tab, zone titles from strings.ts by id („Eingang“, „Teile“, „Datenspeicher“, „Externe Systeme“), no node links. null: the section and its rail link are left out (decision 5.3).

5. Decisions on the build

Decided 2026-11-01: 5.1 A, 5.2 A, 5.3 A, 5.4 B (one PR).

5.1 · where the map is stored · A

A · new column repo_map (recommended). One additive ALTER TABLE … ADD COLUMN. Cost: two map columns on revisions, one per scope, and the store maps each to its page kind.

B · one map for both scopes. Needs revisions_map_scope dropped; SQLite cannot drop a constraint, so the table is rebuilt (copy, drop, rename) while pages.current_revision_id references it, foreign keys on (kit's DSN) and each migration in its own transaction, where PRAGMA foreign_keys cannot be switched. Workable with defer_foreign_keys, but a rebuild of the table holding every page's history for one column's name.

5.2 · which step draws it · A

A · its own step after the subject steps (recommended). Reads the finished description, draws once per run; the prompt and the check stay apart from the describe prompt. Cost: one call per run per repository.

B · every describe step carries the map in its patch. No extra call, but every step's output grows, and the map is drawn from one part at a time and corrected step by step.

C · the project step returns this repository's map too. No extra call, but the project prompt grows a second job, and a project step that is skipped (projectStands) leaves the repository without a map.

5.3 · no map yet · A

A · section left out until drawn (recommended). The project page's rule: no placeholder promising a map that may not come (a repository whose run is spent, or none runs).

B · placeholder „Noch keine Karte“ while a run is expected, like the project's map_expected. Needs that flag on the repository detail too.

5.4 · PR order · B

A · PR 1 (UI) first, PR 2 (map) after (recommended). The layout fix ships without waiting on a migration and a prompt; PR 2 adds one section to a page that already has its place.

B · one PR. One review, but the UI waits on the riskier half.

6. Tests and gate

  • UI (pages.test.tsx): start tab per page; hash opens and writes the tab; a rail link into the other tab switches and lands on the anchor; search filters, highlights, counts, Escape clears, typing on the other tab switches; repository page with the project fetch failed still renders; „Geteilte Daten“ on the project, „Entitäten“ on the repository; full-view node link navigates.
  • Backend: migration applies on a database holding 0001 data; CheckRepoMap table tests (zones, caps, self edges, duplicates); map step happy path, null, broken map carried, calls spent skips; a merge after a run keeps the map; repository detail returns it; .md export; openapi in step with api.go.
  • Seen running: both pages driven with Playwright against compose.dev.yaml: top edges equal (rail, breadcrumb, first column line), sticky rail and breadcrumb while scrolling, narrow fallback at 1000px.
  • Gate: make check before each push.

7. Risks

  • Stale repository map. The inside of a repository changes faster than its place in the system, and only a baseline run redraws the map. Accepted (merges do not redraw); the revision list shows when it was drawn.
  • A map drawn from prose. The map step sees the description, not the code; it is as good as the summary's structure part. A map that disagrees with the code is corrected by the next run's description, then its map.
  • Second fetch on the repository page. One more request per view; the project endpoint is already served for the project page and cheap. Failure degrades to no rail group, no problem block.
  • Sticky elements and alignment. Rail and breadcrumb stick on the same top; checked by measurement in Playwright, not by eye.
