1. Where phase 1 left things

A source is a project (a Bitbucket project listed from the REST API, or a static folder of hand-entered clone URLs). Each repository is a bare, full-history clone at ALMANACH_REPOS_DIR/<key>/<slug>; source_repos records its branch, head_commit and state. One sequential poller fetches every ALMANACH_SYNC_INTERVAL. Nothing reads the clones yet.

The wiki is built from deltas alone: one note per merged PR, folded by one model call into the repository and project descriptions. Everything here keeps that machinery: same pages, same statements, same ceilings, same provenance rules, same single serial worker.

Three facts found while reading the code shape the plan more than the brief suggests:

  • The wiki only knows noergler's projects. store.Projects reads FROM projects, store.Repos reads FROM repos, and projects.team is NOT NULL. A static source whose project never got a note has no row there. This plan turns it around: the source is the starting point, the wiki lists sources, and a note for a repository that is no source is ignored (section 5a, D7, D10).
  • Provenance is PR-keyed in code, not only in the schema. appendSource dedupes on PRKey, attach and render take a store.QueuedNote, Page.SourcePR is a string. All of it generalises to a source with a kind.
  • A fold rewrites the whole page. Ten baseline steps that each return the whole 40-statement page pay ten times for output they mostly copy, and each copy is a chance to lose a statement about a part the step never read (decision D2).

2. Overview

3. A run, step by step

A run documents one repository at one commit, pinned when the run is enqueued. Each step is at most one model call, so a step is the unit the worker interleaves with notes, retries after a gateway hold, and resumes after a restart. A full run on a mid-sized repository is about eight calls; the cap is ALMANACH_BASELINE_MAX_CALLS.

Step 0: list the tree (no call)

  • git ls-tree -r -l -z <sha> with core.quotePath=false (umlauts stay paths), ported from ../rongo's ListEntries: path, mode, size.
  • Code filters before any model sees a path: mode 100644/100755 only (no symlink, no submodule pointer); size over fileMaxBytes (100 kB) dropped by its size, never read; a fixed blocklist of vendored and generated paths (vendor/, node_modules/, third_party/, dist/, build/, target/, .git*, lockfiles, *.min.*, *.pb.go, *_generated.*, *.snap) and binary extensions. A file whose first 8 kB hold a NUL byte is dropped when read.
  • Docs and manifests are picked by code, deterministically: README*, AGENTS.md, CLAUDE.md, ARCHITECTURE*, HOW_IT_WORKS*, CONTRIBUTING*, docs/**/*.md, go.mod, package.json, pom.xml, build.gradle*, Cargo.toml, pyproject.toml, compose.yaml/docker-compose*, Containerfile/Dockerfile, Makefile, openapi*.yaml; root first, then by depth, up to docsMaxBytes (160 kB).

Step 1: catalogue (cheap model, one call)

The catalogue model gets the filtered listing (path and size; over 4000 entries it gets directories with file counts and bytes instead, two levels deep, and names the files of the directories it picks in a second field) plus the first 60 kB of the docs. It returns the repository's subjects: "authentication", "billing run", "the import pipeline", each with a one-line purpose and the files that make it up, most important first. Strict schema, never streamed.

Code holds the answer to rules the model cannot bend: a path not in the filtered listing is dropped (the model inventing one), a subject is cut to stepMaxBytes (240 kB) in the model's order, an empty subject goes, the subject count is cut to MAX_CALLS − 3. The result is stored on the run as its plan. A file may belong to two subjects; flows overlap.

Step 2: overview (strong model, one call)

Reads the docs and manifests from step 0 with the current repository page. Writes the summary (what the repository is for, its main parts, what it talks to) and the statements that span the whole repository. Code chose the input, not the catalogue: the overview must not depend on a cheap model's taste.

Steps 3 … n: one per subject (strong model, one call each)

Reads one subject's files at the pinned commit through one git cat-file --batch process (../rongo's Reader, size refused before read), plus the current page and the subject's name and purpose. Answers with a patch (decision D2): new statements, edits by id, ids to drop, ids confirmed unchanged (D12), optionally a new summary. Code applies it on the current page, then the unchanged rules: attach (ids, Swiss spelling, provenance), check (count, prose runes, name, files), identical means no revision. The prompt states the headroom ({repo_chars} of {repo_max_chars}, statements left, subjects left) so the last subject is not the one that finds the ceiling.

A rewrite over a ceiling ends the subject steps: every later subject would meet the same full page, one paid call each. The run goes on to the project step and finishes partial.

Last step: project (strong model, one call)

Folds the repository's new summary and statement names (not the code) into the project description: what this repository holds, by slug (decision D5). The existing merge rule "the project description is folded from the note, not from the repository description" gets its one documented exception here.

4. The run's states

5. Reconcile: monthly, and on demand

Between runs the notes are the deltas. They are narrow by design: a note says what one review saw, and a push without a PR, a PR noergler did not review, or a fact no review touched never reaches the page. A reconcile run catches that: it reads what changed in the code since the documented commit, whatever the notes said about it, and folds it into the page without dropping what the PRs taught (D12).

The documented commit of a repository is the commit of its last done run. Triggers:

  • Monthly: the poller enqueues a reconcile for a repository whose head moved since its documented commit and whose last run finished more than ALMANACH_BASELINE_RECONCILE ago (default 720h; 0 = buttons only), if the source has auto_describe on. An unchanged repository costs nothing.
  • Aktualisieren (button): the same reconcile, now.
  • Neu beschreiben (button): a full run at the head with a fresh catalogue, for when the catalogue itself is stale (a restructured repository). Folds into the page like every run.

A reconcile, step by step:

  1. Reachable? git merge-base --is-ancestor <documented> <head>. Not an ancestor (a rewritten branch) or missing: a full run.
  2. What changed. git diff -z --raw --no-renames --no-abbrev <documented>..<head> (../rongo's ChangedEntries, with modes and sizes), through the same filters as step 0.
  3. Map onto the catalogue. A changed or deleted path in a subject's files touches that subject. Paths in no subject go to a catalogue step that may only add them to an existing subject or open a new one. Changed bytes over half of the catalogued bytes: a full run instead.
  4. Map onto the page. The statements whose files intersect the changed paths are named by id in the subject's prompt, with the deleted paths: code's provenance points the model at what to check.
  5. The touched subjects get a step, plus every subject the last run skipped (a ceiling, a failed call): a partial run is finished by the next reconcile instead of being forgotten. Then the project step, only if the repository summary changed.

A reconcile that ends with no revision (the code changed, the facts did not) still records its commit. Otherwise the page would show the old commit forever and the next month would read the same range again.

5a. The source is the starting point

PR notes and clones meet on one key, (project_key, slug). The rule that keeps the two from fighting is simple: a repository exists for Almanach once it is a source repository, and only from then on are noergler's deltas folded. The baseline describes it as it stands; the notes refine that.

  1. No source repository, no note. A delivery whose (project_key, repo_slug) names no row in source_repos is answered 202 {"status":"ignored"} and logged as webhook_processed outcome=ignored with project and repository, so a misspelled key shows up in the log. Nothing is stored: not the delivery, not the note, not the structure. The envelope is still checked first (a bad body is a 422 as before), and noergler marks a 2xx as sent, so an ignored note is never resent.
  2. A repository's notes wait while one of its runs is open. The worker takes the oldest queued note whose repository has no queued or running run (D6). A note that arrives during a run stays queued until the run is done.
  3. After a run, every waiting note is folded. Even one whose PR the run's commit already contains: a note carries what the code cannot show (the rule's reason, the ticket, the intent the review saw), and the PR data is never dropped. Folding a fact the page already holds is an identical rewrite, no revision; it costs one call per waiting note.
  4. No run open, no wait. A note for a repository whose clone is still on its way, or whose source has auto_describe off and was never described, folds onto the page as it is. The first run later folds into that page (D1).

6. Decisions

Each one is a recommendation with its options and its cost. All recommendations accepted 2026-10-30.

D1 · Fold, not replace

Recommend fold. A baseline step goes through attach/check like a note: kept ids keep their sources, ceilings and identical-rewrite hold, PR-derived statements survive and are refined. On an empty page a fold is a replace anyway.

Cost: a page full of shallow PR statements constrains the baseline (statement slots, prose budget). If that bites, a "replace" button can come later; it is a new revision, history keeps the old one.

D2 · Read by subject; answer with a patch

Recommend a catalogue of subjects (section 3, step 1) over directory groups. A flow like authentication spans handlers, middleware and the store; a directory group shows the model one third of it per call and leaves it to stitch three partial statements together. Directories still bound the catalogue's input for large repositories.

Recommend a patch answer for subject steps ({summary|null, statements[], drop[], confirmed[]}, unlisted ids kept as they are, confirmed ones per D12) over the full-page rewrite the notes use. Output drops from up to ~20k tokens per step to what the subject adds; a step cannot lose a statement about a part it never read. The full page is still in the prompt so the model can merge duplicates (edit one id, drop the other).

Cost: the catalogue is a model's grouping, less reproducible than directories; code validates every path and stores the plan, and a reconcile reuses it. The patch is a second schema and an applyPatch before attach; the overview and the project steps keep the full-description schema.

D3 · Trigger and cadence

Recommend four triggers. Automatic on a clone's first ready (the transition from an empty head_commit, so repositories already cloned when this ships are not all described at once). Automatic monthly reconcile (section 5). Two buttons per repository: Beschreiben / Aktualisieren (the first run, or a reconcile now) and Neu beschreiben (a full run with a fresh catalogue). The automatic ones obey a per-source switch auto_describe, default on, a checkbox in the create and access forms. No run on every head move: between runs the notes are the deltas.

Options: the switch on by default (recommended) or off, so that every first run is a click. Repositories already cloned when this ships are not described automatically; each gets its Beschreiben button.

Cost: a new Bitbucket project of 60 repositories with the switch on is 60 first runs, roughly $100–$350 by the table above; after that a month of changes per repository is a few subject steps. The switch is the lever; the form shows the cap per run next to it. A global budget would be firmer but needs reliable prices from the gateway, which it does not always report.

D4 · Cost ceilings

Recommend calls and bytes per run as the hard caps, checked before each call (table in section 3), every call in llm_calls with its outcome, purpose and run id, and the run's cost as the sum, a 3-decimal string, on the source page.

Cost: no hard money cap per run: the gateway prices after the fact and sometimes not at all. Calls × step bytes bounds it from above.

D5 · The project page

Recommend one project step at the end of each run (reconcile: only when the summary changed). Without it a static source's project page stays empty forever: no note will ever come for it.

Cost: one call per run, and N repositories described in a row rewrite the project page N times. It is a small call (summaries, not code), and serial, so the N folds do not race.

D6 · Notes first, except their own repository's run

Recommend the worker takes the oldest queued note whose repository has no open run; when there is none, one step of the oldest open run; then it looks at the notes again. A note of a repository with an open run waits for it and is folded after it (section 5a). Runs among themselves: oldest first, one run to its end before the next starts, so pages are not left half described across many repositories.

Options: this order (recommended), or strict oldest first across notes and steps, where a burst of 60 first runs (about 8 calls and several minutes each) holds every merge's note back for an hour or more.

Cost: it bends "oldest first" for the queue as a whole; AGENTS.md and HOW_IT_WORKS change their wording with it. A note is a small, timely delta; a run is minutes of calls, and 60 queued runs would otherwise hold every merge's note back for an hour. Serial still holds: one fold or step at a time, each reading the current page, and no step ever sees a fact newer than its commit.

D7 · The wiki lists the sources

Recommend the read side keys on the sources: a project is listed when it is a source, a repository when it is a source repository. Projects, Repos, ProjectExists, RepoExists read sources/source_repos and left-join the feed's projects for the team line, shown when noergler has delivered for the key.

Options: list sources (recommended), or list sources and noergler's projects together, which keeps showing projects that never update again under D10.

Cost: projects known only from notes, with no source, leave the list until a source is created for them (D11). The four queries change their driving table, and a source created with no clone yet shows an empty project until its first run. Keeping noergler's projects/repos as the list would leave static sources unreachable, the case this phase exists for.

D10 · An ignored note is not stored

Recommend a delivery for a repository that is no source is answered 202 ignored, logged with its key, slug and PR, and written nowhere: no deliveries row, no structure upsert, no note_calls. The check runs after the envelope is validated, inside the ingest transaction, against source_repos.

Options: store nothing (recommended); store the delivery as ignored for audit, never folded; or store and hold it, folded once a matching source appears, which contradicts "deltas only from the source on".

Cost: a note ignored on Monday is not there when the source is created on Tuesday; the first run reads the code that PR produced, so the fact is not lost, its PR chip is. Storing ignored deliveries would keep an audit trail, but deliveries is the raw material the wiki can be rebuilt from, and these must never be rebuilt into it. The webhook's request contract is unchanged; its 202 body gains a third status.

D11 · Pages from before the sources

Recommend notes and pages that exist when this ships, for repositories that are no source, stay in the database untouched and unlisted (D7). When a source with that key and slug is created, the page is listed again and the first run folds into it, its PR facts held by D12. A note still queued at upgrade for a repository that is no source is marked consolidated by the worker with the same ignored log line, so the queue is not blocked by notes that will never fold.

Options: keep them unlisted (recommended); delete them in the migration, irreversibly; or keep them listed as frozen read-only pages.

Cost: rows that nothing lists. A cleanup migration that deletes them was considered and refused: it cannot be undone, and a source created later would start without what those PRs taught.

D12 · A run checks PR facts against the code, it does not erase them

Recommend every run, first or reconcile, treats what the PRs taught as claims to verify:

  • The subject prompt shows, beside the files, the statements that rest on them with their sources, and for a reconcile the titles and change kinds of the notes folded since the documented commit: "this is what the reviews said; check it against the code, correct it, complete it, add what they missed".
  • A patch never drops an id it does not name (D2). An edit keeps the statement's PR sources and appends the Basis source.
  • A statement with a PR among its sources may be dropped by a run only when none of its files exists at the run's commit, which code checks against the tree listing. Any other drop of it rejects the patch whole, like an unknown id. A PR statement without files can only be dropped by a note.
  • The patch may name ids it confirmed unchanged. Code stores the commit on the statement as checked, a field of its own, not a source. A rewrite that changes only checked is still a revision: the page now says which commit vouches for the fact. The UI shows "geprüft 4e1f0c2" beside the chips: which PR facts the current code still backs, at a glance.

Options: these rules (recommended); drops allowed freely, which lets a model wipe what the PRs taught; no drops at all, which leaves facts about deleted code behind; no checked, simpler but without a freshness signal. With checked, a monthly reconcile usually writes one revision per repository.

Cost: a wrong PR fact whose files still exist can be rewritten but not removed by a run, and stays until rewritten or a note drops it. Rejecting a patch whole for a forbidden drop costs that subject's call. The prompt carries the notes' titles, a few hundred tokens a month.

D8 · A second, cheaper model

Recommend ALMANACH_CATALOGUE_MODEL, an llmwire profile id, optional; unset means ALMANACH_MODEL. Validated at startup exactly like the first (strict schema support, listed alias), each its own inference.Client.

Cost: a second variable and a second startup check. Unset, the catalogue costs a strong call, still one per run.

D9 · A baseline source is a chip that does not link

Recommend store.Source gains kind ("pr" | "baseline", omitted = pr, so every stored statement reads unchanged) and commit. A statement a step touches gains baseline@<sha> once per commit, like a PR once per PR. UI: Basis 4e1f0c2, title with the date, no link: there is no page for a commit.

Cost: a repository reconciled every month collects one Basis chip per month on the statements whose text changes, as it collects PR chips. Collapsing to the latest baseline chip is a one-line change if that reads as noise.

7. Data model: migration 0004

-- 0004_baseline.sql (sketch)
ALTER TABLE sources ADD COLUMN auto_describe BOOLEAN NOT NULL DEFAULT true;

CREATE TABLE baseline_runs (
    id BIGSERIAL PRIMARY KEY,
    project_key TEXT NOT NULL,
    slug TEXT NOT NULL,
    mode TEXT NOT NULL CHECK (mode IN ('full', 'reconcile')),
    trigger TEXT NOT NULL CHECK (trigger IN ('manual', 'first_ready', 'monthly')),
    base_commit TEXT NOT NULL DEFAULT '',        -- reconcile: the documented commit
    commit TEXT NOT NULL,                         -- pinned at enqueue
    state TEXT NOT NULL CHECK (state IN ('queued', 'cataloguing', 'describing', 'project', 'done', 'failed')),
    step INTEGER NOT NULL DEFAULT 0,
    steps INTEGER NOT NULL DEFAULT 0,
    plan JSONB,                                   -- subjects with their files and sizes
    attempts INTEGER NOT NULL DEFAULT 0,          -- gateway failures of the current step
    calls INTEGER NOT NULL DEFAULT 0,
    bytes BIGINT NOT NULL DEFAULT 0,
    skipped INTEGER NOT NULL DEFAULT 0,
    error TEXT NOT NULL DEFAULT '',
    queued_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    started_at TIMESTAMPTZ,
    finished_at TIMESTAMPTZ,
    FOREIGN KEY (project_key, slug) REFERENCES source_repos (project_key, slug) ON DELETE CASCADE
);
CREATE UNIQUE INDEX baseline_runs_active_idx ON baseline_runs (project_key, slug)
    WHERE state NOT IN ('done', 'failed');
CREATE INDEX baseline_runs_queue_idx ON baseline_runs (queued_at) WHERE state NOT IN ('done', 'failed');

ALTER TABLE revisions ALTER COLUMN source_pr_key DROP NOT NULL,
    ADD COLUMN source_kind TEXT NOT NULL DEFAULT 'pr' CHECK (source_kind IN ('pr', 'baseline')),
    ADD COLUMN source_commit TEXT,
    ADD COLUMN baseline_run_id BIGINT,
    ADD CHECK ((source_kind = 'pr') = (source_pr_key IS NOT NULL)),
    ADD CHECK ((source_kind = 'baseline') = (source_commit IS NOT NULL));

ALTER TABLE llm_calls ALTER COLUMN source_pr_key DROP NOT NULL,
    ADD COLUMN source_kind TEXT NOT NULL DEFAULT 'pr' CHECK (source_kind IN ('pr', 'baseline')),
    ADD COLUMN source_commit TEXT,
    ADD COLUMN purpose TEXT NOT NULL DEFAULT 'merge' CHECK (purpose IN ('merge', 'catalogue', 'overview', 'subject', 'project')),
    ADD COLUMN baseline_run_id BIGINT;

A step's revision and the run's step advance land in one transaction (store.ApplyBaselineStep, under the same page advisory lock as InsertRevision): a crash between them would otherwise fold the same subject twice after the restart.

9. API

  • POST /webhooks/noergler: request unchanged; the 202 body gains {"status":"ignored"} beside accepted and deduped (D10).
  • POST /api/sources/{key}/repos/{slug}/describe with {"mode":"reconcile"|"full"} (reconcile means full before the first run): 202 {"status":"queued","run_id":…}; 409 when a run is open; 422 when the clone has no head yet; 404 with the feature off. Logged with the forwarded user like the other writes.
  • GET /api/sources/{key}: each repository gains baseline, null before the first run: run_id, state, mode, commit, documented_commit, step, steps, skipped, cost_usd (3 decimals, omitted when unpriced), started_at, finished_at, error. The source gains auto_describe, writable in POST and PATCH.
  • Wiki routes: a revision gains source_kind and source_commit (source_pr_key is "" for a baseline); a statement's source gains kind and commit, the statement checked (a commit or ""). /api/projects and below list sources (D7).
  • backend/api/openapi.yaml in step with all of it.
